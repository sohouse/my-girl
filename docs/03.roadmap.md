### Phase 7：实现角色记忆功能

1. 实现角色的轻量记忆功能，用于保存用户在聊天中透露的重要信息。
2. 记忆功能优先采用结构化数据库方案，MVP 阶段暂不引入向量数据库、复杂长期记忆系统或相似度检索。
3. 角色记忆用于回答时增强角色连续性，例如记住用户生日、喜好、讨厌的事情、重要日期、称呼偏好等。
4. 聊天过程中，系统可以从用户消息中识别值得长期保存的信息，并写入 `character_memories` 表。
5. 记忆提取需要由 AI 返回结构化 JSON，避免直接保存整段聊天内容。
6. 不是所有聊天内容都应该进入记忆，只保存对长期陪伴有价值的信息。
7. 记忆类型至少包括：
   1. `birthday`：用户生日。
   2. `preference`：用户喜好。
   3. `dislike`：用户讨厌或排斥的内容。
   4. `important_date`：用户重要日期或纪念日。
   5. `relationship`：用户提到的重要关系。
   6. `nickname`：用户希望角色使用的称呼。
   7. `note`：其他重要长期信息。
8. 记忆需要包含 `confidence` 字段，用于表示提取可信度。
9. 对于日期类记忆，需要结构化保存日期信息，例如 `date_month`、`date_day`、`date_exact`。
10. 角色生成回复时，应读取当前用户与当前角色相关的有效记忆，并注入到 AI prompt 中。
11. 注入 prompt 的记忆数量需要有限制，避免 prompt 过长。
12. 用户刷新页面或重新进入聊天后，角色仍然可以使用已保存的记忆。
13. 后续邮件发送功能可以通过 `memory_id` 引用日期类记忆，但本 Phase 只负责保存记忆事实，不负责发送邮件。
14. MVP 阶段可以先不做用户手动编辑记忆，后台维护或用户侧记忆管理留到后续 Phase。

#### 建议数据表

1. `character_memories`

字段建议：

- `id`
- `user_id`
- `character_id`
- `type`
- `key`
- `value`
- `meaning`
- `date_month`
- `date_day`
- `date_exact`
- `confidence`
- `source`
- `source_message_id`
- `enabled`
- `created_at`
- `updated_at`

字段说明：

- `type` 表示记忆类型，例如 `birthday`、`preference`、`important_date`。
- `key` 表示结构化记忆键，例如 `user_birthday`、`favorite_food`。
- `value` 表示记忆内容。
- `meaning` 表示这条记忆对角色陪伴的意义。
- `source` 可为 `chat`、`admin`、`system`。
- `source_message_id` 用于追踪该记忆来自哪条聊天消息。
- `enabled` 用于软关闭某条记忆。

#### 记忆提取流程

```txt
用户发送消息
  ↓
正常生成角色回复
  ↓
后台异步分析用户消息是否包含长期记忆
  ↓
AI 返回结构化 JSON
  ↓
服务端校验 JSON
  ↓
写入或更新 character_memories
```

#### **验收标准**

1. 用户在聊天中透露生日、喜好、讨厌内容、重要日期等信息后，系统可以提取并保存为结构化记忆。
2. 记忆保存前需要通过 Zod 或等价方式校验结构。
3. 同一用户、同一角色下的记忆需要隔离，不同角色不能混用记忆。
4. 角色后续回复可以使用已保存记忆，体现连续性。
5. 日期类记忆需要保存可供后续邮件功能引用的结构化日期字段。
6. 不引入复杂向量数据库或长期记忆系统。
7. 同一用户的同一信息如果重复则简单覆盖已有信息

### Phase 8：实现角色通过 email 自动发送消息功能

1. 实现角色通过 email 主动向用户发送消息的功能。
2. 邮件发送依赖 Phase 7 的角色记忆功能，可以通过 `memory_id` 引用用户的重要日期记忆。
3. cron 只负责定时唤醒邮件检查任务，不直接承担所有业务日期判断。
4. 邮件检查任务需要按 `Asia/Shanghai` 日期计算当天是否有应发送事件。
5. 邮件触发来源包括：
   1. 固定公历日期，例如情人节、520、圣诞节。
   2. 后台维护的自定义日期，例如长假第一天、活动日、运营指定纪念日。
   3. 用户个人重要日期，例如生日、纪念日。
   4. 从 `character_memories` 中引用的重要日期记忆。
   5. 可选 cron 表达式规则，例如每周五、每月 1 日。
6. 邮件事件统一维护在 `email_events` 表中，用于描述“哪一天、为什么发、发给谁、由哪个角色发”。
7. `email_events.memory_id` 可为空：
   1. 系统节日和后台自定义日期不需要引用记忆。
   2. 来自聊天记忆的重要日期需要引用 `character_memories.id`。
8. `email_events` 中必须保存日期意义，供 AI 生成邮件内容时使用。
9. 来自记忆的邮件事件可以保存 `title`、`meaning` 和日期字段快照，方便后台单独调整邮件发送语义。
10. 不允许把聊天提取出来的日期事实在邮件表中作为另一套独立事实维护；事实源仍然是 `character_memories`。
11. 邮件发送前必须检查发送日志，确认同一用户、同一角色、同一事件、同一日期没有发送过。
12. 邮件发送成功或失败后都需要写入 `email_send_logs`。
13. 邮件内容由 AI 根据角色人设、用户信息、日期意义、相关记忆生成，再通过 Resend API 发送。
14. 后台需要支持维护邮件事件，包括新增、编辑、启用、停用固定节日和自定义发送日期。
15. MVP 阶段暂不引入复杂队列或第三方节假日 API。长假和特殊节日优先通过后台维护或每年导入节假日数据实现。

每日检查流程

cron 定时触发
↓
进入邮件检查接口
↓
校验 CRON\_SECRET
↓

↓

↓

↓

↓

↓
写入 email\_send\_logs

#### **验收标准**

1. 可以通过每日 cron 自动触发邮件检查。
2. 可以通过后台或接口手动触发同一套邮件检查逻辑。
3. 可以维护固定节日、自定义日期、用户重要日期对应的邮件事件。
4. 来自聊天记忆的重要日期邮件事件，需要通过 memory\_id 关联原始记忆。
5. 同一用户、同一角色、同一事件、同一日期不会重复发送。
6. 邮件内容能够结合角色人设、日期意义和相关记忆生成。
7. 邮件发送成功和失败均有日志可查。
8. MVP 阶段不依赖复杂队列、向量数据库或第三方节假日 API。

### Phase 10：实现 R2 文件存储

1. 实现 Cloudflare R2 文件存储，用于替代当前 `/public/uploads` 的本地图片存储。
2. R2 图片允许公开访问，前端页面直接使用公开 URL 展示图片。
3. R2 存储只在服务端调用，`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY` 等密钥不得暴露到前端。
4. 继续沿用当前对象 key 规则：

```txt
uploads/users/{userId}/{scene}/{timestamp}-{nonce}.{extension}
```

1. 第一版支持的存储场景包括：
   - `custom-character-avatar`：用户自定义角色基础形象图片
   - `ai-generated-image`：聊天过程中生成的 AI 图片
2. 自定义角色上传基础形象时，图片保存到 R2，并在 `characters` 表中保存：
   - `baseImageUrl`：R2 公开访问 URL
   - `baseImageStorageKey`：R2 object key
   - `baseImageStorageProvider`：`r2`
3. 聊天过程中生成的 AI 图片保存到 R2，聊天消息中保存图片公开 URL。
4. 保留 `local-public` 存储实现作为本地开发或测试 fallback，但生产路径默认使用 R2。
5. 上传图片前必须校验文件类型，第一版只支持：
   - `image/jpeg`
   - `image/png`
   - `image/webp`

### 自定义角色删除与 R2 清理

1. 支持删除用户自定义角色。
2. 只有角色创建者本人可以删除自己的自定义角色。
3. 系统预设角色不可删除。
4. 删除自定义角色时，需要同时清理该角色相关的 R2 文件：
   - 自定义角色基础形象图片
   - 该角色所有聊天会话中生成的 AI 图片
5. 删除流程建议：

```txt
用户请求删除自定义角色
  ↓
校验登录态
  ↓
校验角色存在、kind=custom、ownerUserId=当前用户
  ↓
查询角色 baseImageStorageKey
  ↓
查询该角色所有聊天 session 中 type=image 的消息
  ↓
提取可删除的 R2 object key
  ↓
尝试删除 R2 对象
  ↓
删除数据库角色记录
  ↓
依赖 cascade 删除 chat_sessions、chat_messages、memories、email_events 等关联数据
  ↓
返回删除结果和 warning
```

1. R2 删除采用 best-effort 策略：
   - 如果部分 R2 对象删除失败，数据库角色仍然继续删除。
   - 接口返回 `warnings`，说明哪些对象删除失败。
   - 服务端记录删除失败日志，方便后续排查或人工清理。
   - 对象不存在不应导致删除失败。
2. 只删除 `storageProvider = "r2"` 且存在明确 object key 的文件。
3. 对 `local-public`、空 key、默认预设图等资源不调用 R2 删除。

### 暂不做

1. 不迁移历史 `/public/uploads` 文件到 R2。
2. 不做后台文件管理页面。
3. 不做批量文件清理工具。
4. 不做私有桶和签名 URL。
5. 不做用户手动管理聊天图片。
6. 不做语音文件 R2 存储，Phase 5 仍保持音频不落库。
7. 不做复杂对象引用计数；默认自定义角色相关图片只属于该角色生命周期。

### 验收标准

1. 自定义角色基础形象可以成功上传到 R2，并能在页面正常展示。
2. AI 生成图片可以成功上传到 R2，并能在聊天页面正常展示。
3. 数据库正确保存 R2 图片的公开 URL、object key 和 provider。
4. R2 密钥只在服务端读取，前端 bundle 不包含任何 R2 凭证。
5. 删除自定义角色后，数据库中的角色和关联聊天数据被删除。
6. 删除自定义角色时，会尝试删除该角色基础形象和聊天生成图片对应的 R2 对象。
7. R2 对象删除失败时，角色数据库删除仍然成功，接口返回 warning，并记录服务端日志。
8. 未登录用户、非 owner 用户、删除预设角色请求都必须被拒绝。
9. 单元测试覆盖 R2 上传、公开 URL 生成、删除失败 warning、权限校验和自定义角色删除流程。

###### Phase 11：安全加固、上传限制与 Turnstile

1. 对用户上传头像增加安全限制。
2. 对高成本接口增加基础限流，避免 AI、R2、Resend 被恶意刷费用。
3. 接入 Cloudflare Turnstile，用于注册、登录和高风险操作的人机验证。
4. 本 Phase 只做基础防护，不做复杂风控、设备指纹、后台审计系统或付费额度系统。

#### 上传头像安全限制

1. 自定义角色基础形象上传必须限制文件大小。
2. 第一版头像最大大小为 2`MB`。
3. 上传前必须校验：
   - 文件存在
   - 文件大小不超过限制
   - MIME type 只能是 `image/jpeg`、`image/png`、`image/webp`
4. 服务端不能只相信前端校验，必须在 API 或 storage 层二次校验。
5. 上传失败时返回明确但不泄露内部实现的错误，例如：
   - `Unsupported image type`
   - `Image file is too large`
6. 暂不做图片内容审核、EXIF 清理、压缩、裁剪、水印和病毒扫描。

#### Ark 生成图片下载限制

1. Ark 返回生成图片 URL 后，服务端下载图片前必须做安全检查。
2. 只允许下载可信图片域名，第一版至少限制为 Ark/火山引擎返回的官方图片域名。
3. 下载响应必须校验：
   - HTTP 状态成功
   - `Content-Type` 是 `image/jpeg`、`image/png` 或 `image/webp`
   - `Content-Length` 不超过 `2MB`
4. 如果响应缺少 `Content-Length`，下载后仍需检查实际字节大小。
5. 超过大小限制或类型不合法时，不保存到 R2，不写入图片消息。

#### 基础限流

1. 对高成本或高风险接口增加基础限流。
2. 限流维度优先使用：
   - 已登录用户：`userId + action`
   - 未登录用户：`ip + action`
3. 第一版可使用内存限流，适合 MVP 和单实例开发环境。
4. 如果部署到多实例或生产并发增大，后续应替换为 Redis、Vercel KV、Upstash 或数据库限流。

建议默认规则：

```txt
POST /api/characters/custom
- 每用户每 10 分钟最多 10 次

DELETE /api/characters/custom/:characterId
- 每用户每 10 分钟最多 20 次

POST /api/chat/sessions
- 每用户每分钟最多 30 次

POST /api/chat/sessions/:sessionId/messages
- 每用户每分钟最多 10 次

POST /api/chat/sessions/:sessionId/messages/:messageId/voice
- 每用户每分钟最多 5 次

POST /api/chat/sessions/:sessionId/share-card
- 每用户每分钟最多 10 次

POST /api/cron/email-dispatch
- 每分钟最多 3 次
```

1. 超出限流时返回：

```json
{
  "error": "Too many requests"
}
```

1. HTTP 状态码使用 `429`。
2. 限流失败不得触发 Ark、MiniMax、Resend、R2 等三方调用。

#### Cloudflare Turnstile

1. 注册页面接入 Cloudflare Turnstile。
2. 登录页面接入 Cloudflare Turnstile。
3. 自定义角色创建接口接入 Turnstile，避免恶意批量上传头像。
4. 第一版 Turnstile 校验在服务端完成，前端只负责拿到 token 并提交。
5. Turnstile token 必须发送到服务端，由服务端调用 Cloudflare 校验接口：

```txt
https://challenges.cloudflare.com/turnstile/v0/siteverify
```

1. 服务端校验必须使用 `TURNSTILE_SECRET_KEY`。
2. 前端只能使用 `NEXT_PUBLIC_TURNSTILE_SITE_KEY`。
3. Turnstile 校验失败时，接口返回 `400` 或 `403`，不得继续执行注册、登录、上传头像或三方调用。
4. Turnstile 可先保护以下入口：
   - 注册
   - 登录
   - 创建自定义角色
5. 聊天发送消息暂不强制 Turnstile，优先依赖登录态和限流。

#### 暂不做

1. 不做复杂风控评分。
2. 不做设备指纹。
3. 不做验证码失败后的账号冻结。
4. 不做后台风控面板。
5. 不做 Redis/Upstash 分布式限流。
6. 不做图片审核、压缩、裁剪或病毒扫描。
7. 不做用户额度/套餐系统。

#### 验收标准

1. 超过 `2MB` 的自定义角色头像会被服务端拒绝。
2. 非 `jpeg/png/webp` 的头像会被服务端拒绝。
3. Ark 生成图片下载超过 `2MB` 时不会保存到 R2。
4. Ark 生成图片返回非图片类型时不会保存到 R2。
5. 高成本接口超出限流后返回 `429`。
6. 超出限流时不会调用 MiniMax、Ark、Resend 或 R2。
7. 注册和登录页面可以正常展示 Turnstile。
8. 注册、登录和创建自定义角色时必须通过服务端 Turnstile 校验。
9. `TURNSTILE_SECRET_KEY` 只在服务端使用。
10. `NEXT_PUBLIC_TURNSTILE_SITE_KEY` 可以进入前端，其他密钥不得进入前端。

###### Phase 12：自拍照基准图二次生成

1. 当角色在聊天中发送的图片语义为自拍照时，必须参考该角色的基准照片进行二次生成。
2. 普通场景图、环境图、物品图不强制使用角色基准照片。
3. 本 Phase 只处理聊天图片生成链路，不做视频生成、声音克隆、复杂人脸训练或用户手动修图。

#### 自拍照识别

1. 在现有发图判断基础上增加图片类型判断。
2. 第一版至少区分：
   - `selfie`：自拍、照片、看看你、你现在的样子、穿搭自拍、露脸照等角色本人出镜图片。
   - `scene`：窗外、房间、风景、物品、氛围图等不要求角色本人出镜图片。
3. 判断依据来自用户消息、assistant 回复和最近上下文。
4. 如果上下文不明确，但命中了“自拍、照片、看看你、你现在穿什么”等强角色本人出镜语义，优先按 `selfie` 处理。
5. 严肃低落话题、上下文过短、最近已发图等已有阻断规则仍然优先级更高。

#### 基准图来源

1. 系统预设角色使用数据库中保存的 `baseImageUrl` 作为基准图。
2. 自定义角色使用用户上传的 `baseImageUrl` 作为基准图。
3. 如果角色没有可用基准图：
   - 自拍图生成应降级为普通图生成，或直接不生成自拍。
   - 第一版建议直接不生成自拍，并返回文字回复，避免生成与角色不一致的人像。
4. 基准图 URL 必须来自服务端已保存的角色数据，不能从用户消息中直接读取外部图片 URL。

#### Ark 图片二次生成

1. 当图片类型为 `selfie` 且角色存在基准图时，调用 Ark 图片生成接口时必须携带基准图参数。
2. 请求 payload 在原文生图基础上增加 `image` 字段：

```json
{
  "model": "doubao-seedream-5-0-260128",
  "prompt": "结合当前聊天上下文生成角色自拍，保持角色身份、脸部特征、气质与基准图一致。",
  "image": "https://example.com/base-image.png",
  "size": "2K",
  "output_format": "png",
  "watermark": false
}
```

1. prompt 必须明确要求：
   - 保持角色身份一致。
   - 保持脸部特征、发型气质与基准图一致。
   - 符合当前聊天上下文和角色人设。
   - 不添加文字、水印、聊天气泡。
2. `scene` 类型图片继续使用现有文生图 payload，不携带 `image` 字段。
3. 生成后的图片仍沿用 Phase 11 的下载安全检查，包括可信域名、图片 MIME type、大小限制。
4. 保存到 R2 和聊天消息入库逻辑沿用现有图片消息流程。

#### 聊天链路调整

1. `decideImageGeneration` 或等价图片决策逻辑需要返回图片类型，例如：

```ts
{
  shouldGenerateImage: true,
  imageKind: "selfie",
  imagePrompt: "...",
  checklist: []
}
```

1. `sendMessageToSession` 调用图片生成时，需要把角色基准图信息传给图片生成服务。
2. 图片生成服务根据 `imageKind` 和 `baseImageUrl` 决定是否使用二次生成。
3. 如果 `imageKind = "selfie"` 但缺少 `baseImageUrl`，不得调用 Ark 生成人像自拍。
4. 自定义角色删除时，自拍生成图仍作为该角色聊天生成图片参与 R2 清理，不新增独立生命周期。

#### 暂不做

1. 不训练角色专属模型。
2. 不做人脸向量库、相似度评分或人脸识别。
3. 不做图片内容审核、EXIF 清理、裁剪、压缩或水印。
4. 不支持用户在聊天中上传任意参考图来生成自拍。
5. 不做多张基准图融合。
6. 不做用户手动选择“自拍/场景图”的 UI，第一版由服务端根据上下文判断。

#### 验收标准

1. 用户请求“发张自拍”“想看看你现在穿什么”等角色本人出镜图片时，图片生成 payload 会携带当前角色 `baseImageUrl`。
2. 普通风景、房间、物品等非自拍图片生成时，不携带 `image` 字段。
3. 系统预设角色和自定义角色都可以使用各自数据库中的基准图进行自拍二次生成。
4. 自拍生成 prompt 明确要求保持角色身份、脸部特征和气质一致。
5. 缺少基准图时，不调用 Ark 生成自拍图，不写入图片消息。
6. Ark 返回图片仍必须通过 Phase 11 的下载安全检查后才保存到 R2。
7. 生成成功后，聊天消息中保存 R2 图片 URL，并能在聊天页面展示。
8. 单元测试覆盖自拍识别、payload 是否携带 `image`、缺少基准图降级、非自拍不携带基准图和安全下载校验。

###### Phase 14：后台管理系统一期：预设角色管理

1. 建立后台管理系统的第一版基础框架。
2. 第一阶段只做预设角色管理，不做用户管理、AI API 管理、主动邮件运营和完整后台仪表盘。
3. 后台入口与接口必须有管理员权限校验，普通登录用户不得访问后台页面或调用后台接口。
4. 预设角色管理以 `characters.kind = "preset"` 的角色为管理对象，不影响用户自定义角色的数据归属和使用权限。

#### 后台访问与权限

1. 新增后台页面入口，路径为 `/admin`。
2. 后台页面必须要求登录。
3. 登录用户必须具备管理员身份才可以访问后台。
4. 第一版管理员身份通过以下方式实现：
   - 在 `user` 表增加 `role` 字段，取值为 `user` / `admin`。
5. 所有后台 API 必须在服务端二次校验管理员权限，不能只依赖前端页面隐藏。
6. 未登录用户访问后台页面或接口时返回未授权状态。
7. 非管理员用户访问后台页面或接口时返回无权限状态。

#### 预设角色列表

1. 后台需要展示所有系统预设角色。
2. 列表字段至少包含：
   - 角色头像 / 基准图。
   - 名称。
   - 标题。
   - slug。
   - 排序值。
   - 启用状态。
   - 更新时间。
3. 列表需要按 `sortOrder` 升序展示。
4. 后台列表只展示 `kind = "preset"` 的角色。
5. 自定义角色不在本 Phase 的后台中展示和编辑。

#### 预设角色新增与编辑

1. 后台需要支持新增预设角色。
2. 后台需要支持编辑已有预设角色。
3. 表单字段至少包含：
   - `slug`：角色唯一标识，创建后不建议频繁修改。
   - `name`：角色姓名。
   - `title`：角色标签或简短定位。
   - `persona`：人设。
   - `background`：成长背景。
   - `speakingStyle`：说话风格。
   - `catchphrases`：口头禅。
   - `motivation`：行为动机。
   - `baseImageUrl`：基准图展示 URL。
   - `baseImageStorageKey`：未来文件清理或迁移使用。
   - `baseImageStorageProvider`：`local-public` / `r2`。
   - `sortOrder`：前台展示排序。
   - `enabled`：是否启用。
4. 表单需要做前端基础校验和服务端 Zod 校验。
5. `slug` 必须唯一。
6. `name`、`title`、`persona`、`baseImageUrl`、`sortOrder` 为必填字段。
7. 保存成功后，前台角色选择页应读取更新后的数据库数据。

#### 启用、停用与删除

1. 预设角色需要支持启用和停用。
2. 停用后的预设角色不应展示在前台角色选择列表中。
3. 停用已有角色不应删除历史聊天记录。
4. 第一版不做物理删除预设角色，避免误删影响已有聊天会话、记忆、邮件事件和分享卡片。
5. 如确需删除，后续 Phase 再增加软删除与依赖检查。

#### 数据库调整

1. `characters` 表需要支持预设角色启用状态。
2. 建议新增字段：

```txt
enabled boolean not null default true
```

1. 如选择 `user.role` 作为管理员权限方案，需要在 `user` 表新增：

```txt
role text not null default 'user'
```

1. 所有 migration 需要保持现有数据可用。
2. 已有 4 个预设角色默认 `enabled = true`。
3. 用户自定义角色默认也可以保持 `enabled = true`，但本 Phase 后台接口不得编辑 `kind = "custom"` 的角色。

#### 后台 API

1. 新增后台角色管理 API，建议路径：
   - `GET /api/admin/characters/presets`
   - `POST /api/admin/characters/presets`
   - `PATCH /api/admin/characters/presets/:characterId`
   - `PATCH /api/admin/characters/presets/:characterId/enabled`
2. API 返回错误信息应明确但不暴露内部实现。
3. 所有写操作必须校验：
   - 当前用户已登录。
   - 当前用户是管理员。
   - 目标角色存在。
   - 目标角色 `kind = "preset"`。
   - 请求体通过 Zod 校验。
4. 管理端更新预设角色时，需要更新 `updatedAt`。
5. 前台 `/api/characters` 或等价角色列表接口需要过滤停用预设角色。

#### 管理页面体验

1. 后台页面优先做实用、清晰、可扫描的信息结构。
2. 首页进入后台后，第一屏应直接看到预设角色列表，而不是营销式介绍页。
3. 角色编辑可以使用抽屉、弹窗或独立编辑页，优先选择与项目现有组件风格一致的方式。
4. 长文本字段需要使用多行输入。
5. 口头禅可以第一版使用换行文本保存，继续兼容当前 `catchphrases` 存储方式。
6. 保存、取消、启用、停用等操作需要有明确反馈。
7. 表单保存失败时，不应丢失用户已输入内容。

#### 暂不做

1. 不做用户管理后台。
2. 不做 AI API Key 后台管理。
3. 不做主动邮件运营后台。
4. 不做后台首页数据仪表盘。
5. 不做复杂 RBAC、权限组、操作审批流。
6. 不做预设角色物理删除。
7. 不做图片上传组件；第一版基准图可以先填写 URL，后续再接入后台上传到 R2。
8. 不做后台操作审计日志，后续后台扩展时再统一设计。

#### 验收标准

1. 管理员可以访问后台预设角色管理页面。
2. 未登录用户和非管理员用户不能访问后台页面，也不能调用后台管理 API。
3. 管理员可以查看所有预设角色，并按 `sortOrder` 排序。
4. 管理员可以新增预设角色。
5. 管理员可以编辑预设角色的人设、背景、说话风格、口头禅、动机、基准图和排序。
6. 管理员可以启用或停用预设角色。
7. 停用后的预设角色不出现在前台角色选择列表中。
8. 停用预设角色不会删除历史聊天会话和消息。
9. 后台接口不能编辑用户自定义角色。
10. 预设角色表单输入需要通过前端和服务端校验。
11. 数据库 migration 执行后，已有预设角色仍然可用且默认启用。
12. 单元测试覆盖管理员权限、非管理员拒绝、预设角色新增、编辑、停用、前台过滤停用角色和禁止编辑自定义角色。
13. 修改后需要通过 lint、测试和 build 或等价检查。

###### Phase 15：后台管理系统二期：统一后台入口与用户维护

1. 将后台从单一预设角色管理页面升级为统一后台入口。
2. 后台统一路径以 `/admin` 开始。
3. 本 Phase 只新增用户维护功能和后台导航结构，不做 AI API 管理、邮件运营后台、复杂权限系统或数据仪表盘。
4. 所有后台页面和后台 API 必须继续要求管理员权限。

#### 后台统一入口

1. `/admin` 作为后台首页或默认入口。
2. 后台需要有统一布局，包含：
   - My Girl Logo。
   - 当前后台模块标题。
   - 导航入口。
   - 返回首页入口。
3. 第一版后台导航至少包含：
   - 用户维护：`/admin/users`
   - 预设角色管理：`/admin/characters`
4. 原有预设角色管理能力迁移到 `/admin/characters`。
5. `/admin` 可以默认跳转到 `/admin/users`，或展示两个管理入口卡片。
6. 后台布局需要在桌面和移动端都可用，但不做复杂响应式后台框架。

#### 用户列表

1. 管理员可以查看用户列表。
2. 用户列表字段至少包含：
   - 用户名 / 昵称。
   - 邮箱。
   - 账号角色：`user` / `admin`。
   - 邮箱验证状态。
   - 创建时间。
   - 更新时间。
3. 列表按创建时间倒序展示。
4. 第一版可以不做分页；如果用户数量增长，后续 Phase 再补分页和搜索。
5. 用户列表不得展示密码、token、session token 或第三方密钥。

#### 用户维护

1. 管理员可以编辑用户的基础维护字段。
2. 第一版允许编辑：
   - `name`
   - `username`
   - `displayUsername`
   - `role`
   - `emailVerified`
3. 第一版不允许编辑：
   - `id`
   - `email`
   - `password`
   - `createdAt`
   - `updatedAt`
4. 管理员可以将普通用户设为管理员。
5. 管理员可以将管理员降级为普通用户。
6. 禁止当前登录管理员把自己降级为普通用户，避免后台无人可用。
7. 用户编辑保存后需要更新 `updatedAt`。

#### 后台 API

1. 新增用户维护 API：
   - `GET /api/admin/users`
   - `PATCH /api/admin/users/:userId`
2. 所有 API 必须校验：
   - 当前用户已登录。
   - 当前用户是管理员。
   - 目标用户存在。
   - 请求体通过 Zod 校验。
3. 非管理员访问返回 `403`。
4. 未登录访问返回 `401`。
5. 更新不存在的用户返回 `404`。
6. 禁止管理员通过 API 降级自己。

#### 暂不做

1. 不做删除用户。
2. 不做封禁用户。
3. 不做重置密码。
4. 不做用户搜索、分页、筛选。
5. 不做批量操作。
6. 不做操作审计日志。
7. 不做复杂 RBAC、权限组或多级管理员。
8. 不做查看用户聊天记录、记忆、图片或邮件记录。

#### 验收标准

1. 管理员访问 `/admin` 可以看到统一后台入口。
2. 后台可以在“用户维护”和“预设角色管理”之间切换。
3. 原有预设角色管理功能在 `/admin/characters` 可继续使用。
4. 管理员可以访问 `/admin/users` 查看用户列表。
5. 用户列表展示用户名、邮箱、角色、邮箱验证状态、创建时间和更新时间。
6. 管理员可以编辑用户的 `name`、`username`、`displayUsername`、`role` 和 `emailVerified`。
7. 非管理员不能访问用户维护页面和用户维护 API。
8. 未登录用户访问后台仍会跳转登录或返回未授权。
9. 管理员不能把自己的 `role` 从 `admin` 改成 `user`。
10. 用户维护 API 不返回密码、token、session token 或敏感凭证。
11. 单元测试覆盖管理员权限、非管理员拒绝、用户列表、用户编辑、禁止自降级和敏感字段不返回。
12. 修改后需要通过 lint、测试和 build。
